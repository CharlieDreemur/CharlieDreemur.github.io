怎么验证 agent 生成的 kernel 是正确的？
容差怎么定，谁说了算？

英文问法How do you verify that a generated kernel is correct? · What tolerance do you use, and why not a single 1e-2? · Can you trust the tests the agent wrote for itself?

考过Unity Vector 自己的论文（FlashVector §4.2 Verify 的正确性四档）· 资料：KernelBench-Verified、SOL-ExecBench、PyTorch assert_close · 推断会问，没有 Unity 自己的面经原题，手头也没有别家的面经原题

先弄清楚：每个概念是什么

Reference
被替换掉的 PyTorch 实现。新 kernel 和它吃同样的输入，输出逐个元素比，像拿标准答案对卷子。
容差
允许的数值差。assert_close 的判定是 \(|a - e| \le \text{atol} + \text{rtol}\cdot|e|\)，\(e\) 是 reference 的值。fp32 默认 rtol 约 1.3e-6，bf16 约 1.6e-2。
Bit-identical
输出每个 bit 都一样，容差是 0。计算顺序不变的 rewrite 才做得到。FlashVector 把 attention 的 6 个 kernel 融成 1 个，结果 bit-identical。
Hidden shape
agent 看不到的测试 shape，用来防它只对测试 shape 走捷径。KernelBench-Verified 里，GPT-5.5 写的 ReLU kernel 在输入 shape 等于测试 shape 时原样返回输入，报出 374x。
Harness
跑测试并下判定的固定代码，放在 agent 改不到的地方（见 harness）。

30 秒回答

I compare the kernel against the PyTorch reference on many inputs: different seeds, scaled and negated distributions to hit overflow, underflow and sign branches, and shapes the agent never saw. The tolerance depends on the change. If the rewrite keeps the order of operations, the output must be bit-identical. If it reorders floating point, I use a per-dtype tolerance, about 1.3e-6 relative for fp32 and 1.6e-2 for bf16, because one loose 1e-2 lets a precision downgrade pass. NaN and inf are checked separately. The harness decides, not tests the agent wrote, and it re-checks inside the timing loop. Random testing is evidence, not proof.

Verify 回放的是录下来的 artifact，包括 model weights、有代表性的 input 和对应的 prediction。容差只能收紧，不能放宽，接受的阈值写回 model card。

自己搭 harness：测什么

测什么怎么做防什么
输入多个 seed；再把输入 ×3、×0.01、×(−1)overflow、underflow、符号分支
Shape多个 shape，含 hidden shape、非 2 的幂、tail tile只对测试 shape 走捷径
容差按 dtype 设：fp32 rtol 约 1.3e-6，fp16 1e-3，bf16 约 1.6e-2precision downgrade
特殊值NaN 和 inf 单独查assert_close 默认 equal_nan=False
整个模型whole-model parity，必要时含 backward单个 kernel 对了，组合后不一定对

手算一遍 1e-2 宽在哪。reference 的值是 100 时，fp32 的默认容差允许差 \(10^{-5} + 1.3\times10^{-6}\times100 = 1.4\times10^{-4}\)。KernelBench 原来 atol 和 rtol 都是 1e-2，允许差 \(0.01 + 0.01\times100 = 1.01\)，宽了约 7000 倍，用 TF32 或 BF16 算的 kernel 也能过。

必答点

  • 和 PyTorch reference 比：多个 seed、多种分布、hidden shape
  • 计算顺序不变就要求 bit-identical，变了才按 dtype 给容差
  • fp32 rtol 约 1.3e-6，bf16 约 1.6e-2；一刀切 1e-2 会放过 precision downgrade
  • NaN 和 inf 单独查
  • 判定权在 harness，不在 agent 自己写的 test
  • random test 不等于证明

追问

计时的时候还要再校验吗？

要。有的 kernel 第一次算对，之后跳过计算。GPU MODE 的 leaderboard 模式每次计时迭代都重新生成输入并重新校验。

让 agent 自己写 test 行不行？

不行。KernelFalcon 让 LLM 生成 test harness，原文承认这是一个漏洞。更多钻评测漏洞的例子见 reward hacking。

random test 全过了，能说 kernel 一定对吗？

不能。KernelBench 把 formal verification 列为 future work。AlphaEvolve 的 FlashAttention 改动最后还是请人类专家确认。

数值对了就够了吗？

还要看 memory。KernelBench-Verified 发现，最好的模型写对的 kernel 里有 28% 提高了 peak memory。之后还要看提升是否超过 noise floor。

FlashVector 的四档有哪些没写清？

Figure 3 把 GPU kernel 层写成 "bit-exact tensor compare"，正文却允许改变浮点顺序的 rewrite 走容差。有意的近似由谁批准、看哪些 business metrics，论文也没写。

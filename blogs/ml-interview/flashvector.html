Unity Vector 的 FlashVector：
agent 怎么优化整个 serving stack？

英文问法Walk me through FlashVector. How does the agent optimize the whole serving stack? · How does it know a change is correct and really faster? · How do the agent's changes reach production?

考过Unity Vector 自己的论文（arXiv 2609.17391，2026-09，Unity Vector AI Team 与 Stanford；据 LinkedIn 转发，一作是 2026 年暑期实习生）· 面试官提示会考 "agentic 优化 kernel / CUDA"（2026-10，你转述），很可能指这篇，这是推断 · 没有 Unity 自己的面经原题 · 面试前必读

先弄清楚：每个概念是什么

Serving stack
一次广告请求要穿过的四层：feature processing、model server（Triton）、PyTorch graph、GPU kernel。瓶颈分散在各层，每层要不同的专业知识。
Layer agent
每层一个 agent，四步的接口相同，工具和知识不同。GPU kernel 层用 Nsight 做 profile，model server 层用 eBPF。
Verifier
决定一个改动留不留的固定代码，像阅卷人，考生改不了评分标准。论文 Figure 2 的图中文字是 "fixed verifier the agent cannot edit"。
Noise floor
baseline 一行不改重复跑，指标自己的波动。FlashVector 端到端是 ±6%。
Shadow-traffic canary
把真实请求复制一份给新版本，结果不返回用户。

看图：四层 stack，四步循环加 Refine

30 秒回答

FlashVector takes the kernel-optimization agent idea and applies it to the whole serving stack of Unity's ads models: GPU kernels, the PyTorch graph, the Triton model server and feature processing. Each layer has its own agent running the same four steps: profile, diagnose, optimize, verify. Correctness is tiered by change type, from bit-exact outputs for a deterministic rewrite to a shadow-traffic canary for a config change. Every change is load-tested end to end on replayed production traffic at the latency SLO, and kept only if the gain beats the measurement noise, about six percent. Changes ship as reviewed pull requests. Across six production models, throughput rose 1.1 to 2 times.

四步循环加 Refine

步骤做什么要记住的一点
Profile按层用不同的工具，GPU kernel 用 Nsight，model server 用 eBPF环境也按层分。GPU kernel 在 local simulated environment，model server 和 feature processing 在 production-like load test
Diagnose对照 knowledge base 提假设，按“时间占比 × 预期收益”排序预期收益低于 noise floor 的假设直接跳过
Optimize改代码或配置一轮只做一个改动
Verify先过本层的正确性四档，再过 full-stack load test提升超过 noise floor 才留
Refinerun 结束后跑一次，in-place 写回 knowledge base接受和拒绝的改动都记

要记的规则，细节在各页

  • 正确性四档：deterministic rewrite 要逐元素相等；改变浮点顺序的按 dtype 的容差；有意的近似看 business metrics；配置改动走 shadow-traffic canary（kernel 正确性）
  • Noise floor：端到端 ±6%。落在 2–6% 的提升加样本重测，最多 8 倍，按 \(1/\sqrt{k}\) 收紧到 2.1%（noise floor）
  • Verify globally：本层通过后还要过 full-stack load test，因为 kernel 快了端到端不一定快（局部和端到端）
  • Knowledge base：人写的六类文档，加 agent 写回的 per-model card（knowledge base）
  • 进生产：agent 开 PR，人 review；配置改动的 canary 稳住就采纳，否则丢弃（进生产）
  • 自动触发：新 release 进 fleet，或者在线模型太久没被分析时，循环自己启动，不用人启动

四个 case 的数字

Case改了什么数字
1 model serverTriton Python backend 的 string 反序列化改写成 C++，已合入 Triton 上游函数级 microbenchmark 最高 30×

论文没写什么

  • 用哪个 LLM
  • 用哪个 agent 框架
  • sandbox 用什么技术。"all candidates run sandboxed" 只出现在 Figure 2 的图里（见 sandbox）
  • 一次 run 的成本：token、耗时、并行度都没有数字

这四项不要替论文补答案，适合留到最后当反问。

读论文要小心的两处

  • Case 1 的时间：论文引用的 Triton issue #8348 开于 2025-08，早于 2026 年暑期项目。不要说成实习生的 agent 在暑期发现的
  • Table 4 的 Model B：p99 是 271 ms，超过它 250 ms 的 SLO，论文没有解释

必答点

  • 四层：GPU kernel、PyTorch graph、model server、feature processing
  • 每层同样四步：Profile → Diagnose → Optimize → Verify，run 结束后 Refine
  • 每轮随机抽一层，一轮一个改动
  • Optimize locally, verify globally：本层通过后还要过 full-stack load test
  • 提升超过 noise floor（±6%）才留
  • agent 开 PR，人 review；新 release 进 fleet 时自动触发

追问

为什么不让 LLM 一次生成优化方案？

论文说 LLM 会看错自己的 profile，所以要一个 harness 逐步检查。它还需要精确的 kernel trace（nsys、ncu）和准确的 tensor shape，roofline 分析时才少 hallucinate。

为什么每轮随机抽一层，不先做瓶颈最大的那层？

论文没解释。Algorithm 1 是随机选，没有按各层的时间占比加权，这一点适合当反问。

它用了什么 search？

单链循环，没有 beam、evolution 或 MCTS。论文的精力放在验证和交付上（几种 search 的对比见 search 方法）。

Case 1 的 30× 能说成线上快了 30 倍吗？

不能。30× 是 deserialize_bytes_tensor 这个函数的 microbenchmark。结果表里 retrieval model 的 latency speedup 是 1.67×，两个数口径不同。

这和 Offline Infrastructure 有什么关系？

同一个循环可以搬到 data 和 training pipeline，目标换成 throughput 和 GPU-hour（见 offline pipeline）。这是推断，本岗 JD 没有写 agent 或 kernel。

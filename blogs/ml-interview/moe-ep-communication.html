EP 的 all-to-all 为什么是瓶颈？
NCCL EP、ShortcutMoE、MegaMoE 各做了什么？

英文问法Why is the all-to-all the bottleneck in expert parallelism? · How would you hide or shrink expert-parallel communication in MoE training? · What recent MoE work in Megatron Core have you read about?

考过推断，没有面经问过，依据是团队最近的 release notes 和 PR。

先弄清楚：每个概念是什么

EP 的 all-to-all
每个 MoE 层两次。dispatch 把 token 发到 expert 所在的卡，combine 把结果发回来。基础见 MoE 与 Expert Parallel。
Critical path
expert FFN 要等 dispatch，下一层要等 combine。通信没完，计算只能等。
Dispatcher backend
实现 dispatch 和 combine 的那层库。flex dispatcher 下有四个：DeepEP、DeepEP v2、HybridEP、NCCL EP。另一种 dispatcher alltoall 不走这些 backend，它是默认值。
Receive buffer
每张卡接收 token 的 buffer，收到多少由 router 决定，每步都不一样。

30 秒回答

In expert parallelism every MoE layer runs two all-to-alls: dispatch sends tokens to their experts' GPUs, and combine brings the results back. Both sit on the critical path, so the GPU idles while they run. Megatron attacks this three ways. NCCL EP is a backend whose static mode keeps a fixed receive budget, so it stays CUDA-graph capturable. If a step overflows the budget, it reruns that step once without dropping tokens. ShortcutMoE runs the all-to-alls on a side stream so they overlap attention. MegaMoE fuses dispatch, expert compute and combine into one kernel.

三个方向各做了什么

方向做了什么代价或限制
换 backend
NCCL EP		dispatch 和 combine 做进 NCCL，有 eager 和 static 两种 modestatic 的 budget 不够时，这一步要重跑
Overlap
ShortcutMoE		dispatch 和 combine 的 all-to-all 放到 side stream，和主 stream 上的 attention 同时跑要改模型结构。训练时不支持 CUDA Graph
融合 kernel
MegaMoE		dispatch、expert 计算、combine 合成一个 megakernel，少停顿，少 launch（见 kernel fusion）现有的 MoK 实现要求 EP group 在一个 NVLink domain 内

NCCL EP 的 eager 和 static

ModeReceive bufferCUDA Graph
eager每步按实际收到的 token 数来定大小每步都变，按 CUDA Graph 的限制推断 capture 不了
static固定 budget能 capture

static mode 让 NCCL EP 在溢出时丢掉多出的 token，同时在 GPU 上累计超出量和 peak，不溢出就不用 sync。溢出的那一步改用 dropless（eager）方式重跑一次。然后重建 EP context，把 budget 扩到刚才观测到的 peak，下一步起回到 static mode。

ShortcutMoE 为什么能 overlap

普通 MoE 里 dispatch 要等本层 attention 算完。ScMoE 论文让 routed expert 经 shortcut 处理前一层的 representation，dispatch 就不用等。Megatron 把 dispatch 和 combine 的 all-to-all 放到 side stream 上，和主 stream 上的 attention 重叠，一般做法见 overlap。实际 throughput 的提升比图 1 的上限小得多。

必答点

  • all-to-all 在 critical path 上，一层两次，期间 GPU 空等
  • NCCL EP 的 eager 每步定 receive buffer。static 用固定 budget，能被 CUDA Graph capture，溢出就用 dropless 方式重跑这一步
  • ShortcutMoE：all-to-all 放到 side stream，和 attention 重叠，代价是改模型结构
  • MegaMoE：dispatch、expert 计算、combine 合成一个 megakernel，MoK 实现要求 EP group 在一个 NVLink domain 内
  • flex dispatcher 下四个 backend 并存，还没有定论哪个最好

追问

MegaMoE 的提速都来自 kernel 融合吗？

不全是。对比的那次 run 同时去掉了一部分 recompute 和 offload，也改了 CUDA Graph 的范围，所以不能把提速全算在融合上。

NCCL EP、DeepEP v2、HybridEP 怎么选？

没有官方结论，团队还在 benchmark。下游的 recipe 也各选各的，有的默认 NCCL EP，有的默认 HybridEP，所以不要说哪个已被弃用。

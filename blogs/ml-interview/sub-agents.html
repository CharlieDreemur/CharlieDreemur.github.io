Sub-agent 和 multi-agent：
什么时候拆，context 怎么传？

英文问法When would you split a task across sub-agents instead of using one agent? · A sub-agent starts with an empty context. What goes into its brief? · Do more agents make the system faster or slower?

考过别家面经原题：阿里边缘 BU 一面（校招，发帖 2026-09-03）「如何保证传给子 Agent 的上下文足够完整，不会遗漏关键信息？」「引入多层 Agent 和多个子 Agent 后，执行效率是否会变慢？」（牛客）、蔚来软件开发二面（发帖 2026-09-17）「子Agent返回结果全部正确，但主Agent汇总时出现幻觉，原因是什么，有什么优化方案」（牛客） · Unity 自己的材料：FlashVector 每个 serving layer 有自己的 layer agent，§6 提到 "parallel agent workflows"，没写并行多少个、怎么协调 · 中文面经样本里有 15 帖问 sub-agent 和 multi-agent · 没有 Unity 自己的面经原题

先弄清楚：每个概念是什么

Sub-agent
主 agent 派出去的另一个 agent，有自己的 context，而且从空白开始。像把一件事交给没开过前面那些会的同事，他只知道你写给他的那张纸。
Brief
写给 sub-agent 的任务说明，是它能看到的全部背景。
Planner 和 worker
一种编排方式。planner 是负责拆任务和分任务的主 agent，worker 是干活的 sub-agent。
确定性代码
普通的程序逻辑，不调 LLM。计数、停止条件、哪个结果留下，都写在这里。
串行依赖
后一步要用前一步的结果。这样的两步没法并行。

看图：planner 分任务，确定性代码收结果

30 秒回答

I split in three cases: the subtasks are independent, such as trying several kernel variants in parallel; one context can't hold all the tool output; or the judge must be separate from the author. A sub-agent starts with an empty context, so the brief has to carry the goal, the constraints, what has already been tried and the output format. It returns a summary with evidence, not its whole transcript. Deterministic code collects the results and decides what to keep. The cost is more total tokens and coordination overhead, and tasks with serial dependencies get slower when split, so I don't split those.

什么时候拆，代价是什么

情况拆不拆原因
子任务互相独立，比如并行试几种 kernel 写法拆并行能省 wall time
一个 context 装不下全部 tool 输出拆worker 自己消化原始输出，只交回结论
评审要和作者分开拆同一个 agent 既写码又评判，是论文归纳过的一类失败
步骤之间有串行依赖不拆每多一次交接就多一份 brief 和一次摘要，更慢，还会丢信息

代价有两项。总 token 更多，因为每个 worker 都要重新读一遍背景。协调也有开销。手算一遍，数字是举例。4 个独立子任务各要 10 分钟，串行是 40 分钟，并行大约 10 分钟再加写 brief 和汇总的时间。如果单个 agent 做完要 60K token，4 个 worker 各用 30K 就是 120K，时间省了，token 翻倍。

Brief 写什么。目标、约束、已经试过的、输出格式，四项都要有。sub-agent 看不到主对话，brief 里漏掉的它就不知道。

同类系统怎么编排

系统做法
KernelFalcon控制流写在确定性的 Python 里；默认 4 个并行 worker，各自保留自己的 error context，第一个通过的胜出
Cursor × NVIDIAplanner 给 worker 分配并重新平衡任务；协调协议是一个 markdown 文件
KernelArc按策略分工的并行 agent，每个只改自己的 solution 目录；计数、停止条件、重启都在确定性代码里
FlashVector单链循环，每轮随机抽一层，只做一个改动；并行度论文没写

必答点

  • 三种情况才拆：子任务独立、一个 context 装不下、评审要和作者分开
  • 代价：总 token 更多，协调有开销，有串行依赖的任务拆了更慢
  • sub-agent 从空 context 开始，brief 要带目标、约束、已经试过的、输出格式
  • 返回结论和证据，不返回整段 transcript
  • planner 分任务，worker 并行，由确定性代码收结果

追问

加了多层 agent 和多个 sub-agent，会不会变慢？（阿里边缘 BU 原题）

有串行依赖的任务拆了更慢，因为每次交接都要写 brief 再做摘要。互相独立的任务并行跑才快。

怎么保证传给 sub-agent 的 context 不漏关键信息？（阿里边缘 BU 原题）

brief 用固定模板，四项逐项填。大段材料给文件路径，让 sub-agent 自己读，不靠主 agent 转述。

sub-agent 的结果都对，主 agent 汇总时出了幻觉，怎么办？（蔚来原题）

让 sub-agent 按固定格式返回结论和证据，由确定性代码合并。主 agent 不凭印象重写一遍。

两个 worker 要改同一个文件怎么办？

每个 worker 用自己的 workspace，KernelArc 就让每个 agent 只改自己的目录，别人的成果只读。合并时的覆写问题见 edit tool 的 hash 检查。

为什么评审要和作者分开？

一篇用薄 harness 跑 KernelBench 的 workshop 论文归纳了五类失败，其中一类就是同一个 agent 既计划、又写码、又评判。KDA 的做法是 Claude Code 实现，Codex 每轮 review。

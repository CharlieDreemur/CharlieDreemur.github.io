Agent 的 observability：
记什么，慢了或贵了怎么查？

英文问法How would you design tracing and observability for an agent system? · Token usage suddenly went up. How do you find the cause? · An agent run is slow. How do you tell which layer is the problem?

先弄清楚：每个概念是什么

Trace
一次 run 从头到尾的完整记录，形状是一棵树。像一张带时间的购物小票，每一步花了多久、用了多少 token 都列在上面。
Span
trace 里的一个节点，有开始时间和结束时间。一次 model call 是一个 span，一次 tool call 也是一个 span。sub-agent 是挂在下面的一棵子树。
Metrics
把很多个 run 的 span 汇总出来的数字。成功率、步数、每个 task 的 token、p50 和 p95 latency。
Transcript
一次 run 里模型读到的和写出的原文。metrics 只说明这个 run 失败了，原因要读 transcript。

看图：一次 run 的 trace 树

30 秒回答

I trace each run as a tree of spans: one span per model call and one per tool call, with a sub-agent as a subtree. Each span records latency, input and output tokens, the tool's arguments, and whether it succeeded. On top of that I aggregate metrics: success rate, step count, tokens and cost per task, and p50 and p95 latency. When a run is slow or expensive, the trace shows which span the time or the tokens went to, and I can break it down by tool or by step. I still read raw transcripts, because metrics tell me a run failed, not why.

三层各记什么

层记什么用来回答
Spanlatency、input 和 output token、tool 参数、成功或失败这一步花了多少
Trace一次 run 的全部 span，带上 task id、model 版本和 harness 版本这个 run 为什么失败，时间和 token 去了哪
Metrics成功率、步数、每个 task 的 token 和成本、p50 和 p95 latency这一版整体变好还是变差

Token 突然变多，按这个顺序查

  1. 先在 metrics 上分组，按版本、task 类别和 tool 看，是所有 run 都涨还是某一类涨
  2. 再分清涨的是每次 model call 的 input，还是 model call 的次数
  3. 每次的 input 变大，就查 tool result 是否变大，比如某个 tool 开始返回整份日志（对策见 context compaction）
  4. 次数变多，就查重试是否变多，有没有重复同一个 action（见 tool 失败与重试）
  5. token 数没怎么变、成本却涨了，就查 prefix cache 是否 miss，比如 system prompt 或 tool 定义被改过（见 KV cache）
  6. 最后挑几条最贵的 trace 读 transcript，确认原因

手算一下第 3 条。context 是累加的，一个 tool result 多出 5000 token，之后每次 model call 都要把它再读一遍。它在第 5 步进来，run 一共 20 步，就多出 5000 × 15 = 75000 个 input token。

慢了也用同一个办法。按 span 分解，看时间花在 model call、tool call 还是排队上。

必答点

  • 一次 run 一个 trace，每次 model call 和 tool call 一个 span，sub-agent 是子树
  • span 里记 latency、input 和 output token、tool 参数、成功或失败
  • metrics 看成功率、步数、每个 task 的 token 和成本、p50 和 p95 latency
  • 慢了按 span 分解，看是模型、tool 还是排队
  • token 变多查三样：tool result 变大、重试变多、cache miss
  • metrics 只说明失败了，原因要读 transcript

追问

执行时间长，一定是异常吗？

不一定，跑 benchmark 的 task 本来就慢。阈值按 task 类别分开定，和同类的 p95 比。字节 AI 大模型开发平台一面问过这一句。

Metrics、log、trace 有什么区别？

metrics 是汇总后的数字，适合报警和看趋势。log 是一条条独立的事件。trace 把一个 run 的事件按父子关系串起来，适合定位哪一步出了问题。

有 sub-agent 时，trace 怎么串起来？

整个 run 共用一个 trace id。主 agent 把当前 span 的 id 传给 sub-agent，sub-agent 的 span 都挂在它下面。

怎么记录每轮实验的耗时、token、结果和失败路线？

每个 run 写一条记录，有 task id、版本、成功与否、步数、token、latency 和 trace 的路径。失败的 run 再标上失败类型，方便统计，也避免下次重试同一条路线（见 knowledge base）。

有了 metrics，为什么还要人读 transcript？

读了才知道是 tool 描述有歧义、context 里丢了约束，还是 agent 绕过了检查（见 reward hacking）。Etched 的 kernel 岗 JD 专门写了要细读 transcript。

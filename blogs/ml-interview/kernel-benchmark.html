先弄清楚：每个概念是什么

异步执行
CPU 把 kernel 交给 GPU 就返回，不等它跑完。像下了单就看表，量到的是下单时间，不是送达时间。
synchronize 和 CUDA event
两种计时法。torch.cuda.synchronize() 让 CPU 等 GPU 跑完，再用 host timer 停表，量到的时间含 launch overhead。CUDA event 量的是 GPU 时间。
Warmup
正式计时前先空跑几次，不让初始化的开销算进去。
Baseline
拿来对比的参照实现。它越弱，speedup 越好看。KernelBench-Verified 把 baseline 换成开 TF32 的版本并加上 hidden test 后，GPT-5.5 从 1.43x 掉到 0.88x。
Speed of light
硬件的物理上限，由峰值算力和 memory bandwidth 算出来（见 roofline）。H100 上 BF16 4096² matmul 的下界约 0.138 ms。

30 秒回答

GPU kernels launch asynchronously, so a host timer without a sync only measures the launch. I time with CUDA events, or call synchronize before and after. Then I cut the noise: warm up first, repeat many times and take the median, flush the L2 cache between runs, lock the GPU clock and keep the GPU exclusive. To compare candidates fairly, they run on the same machine, the same build and the same shapes and dtype, in alternating or random order. The baseline has to be strong, like torch.compile with TF32 on, not eager FP32. Finally, anything faster than the hardware's speed of light is a bug, not a win.

怎么计时，怎么去噪

措施防什么谁这么做
同步后再停表只量到 launchPyTorch 文档："time measurements without synchronizations are not accurate"
Warmup初始化被算进去KernelBench 用 3 次 warmup 加 100 次 trial；Triton do_bench 默认 25 ms warmup、100 ms rep
多次取 median个别离群的一次带偏结果CUDA-L1 取 median of bucket averages；GPU MODE 跑到 relative standard error 低于 1% 才停
每次运行前清 L2上一次留在 cache 里的数据do_bench 每次调用前执行 clear_cache
锁时钟、独占 GPU频率变化，别的任务抢 GPUSOL-ExecBench 把 B200 锁在 1,500 MHz；KernelBench 一次只跑一个 kernel
规模调到 1–15 mslaunch overhead 占主导KernelBench v0.1；也可以用 CUDA graph 去掉 launch overhead

手算一遍规模为什么要紧。KernelBench 原来的 ReLU 一次只要 0.013 ms，也就是 13 µs。launch overhead 按 5 µs 算（示意），占了三分之一还多。v0.1 把这题调到 6.97 ms，同样的 5 µs 不到 0.1%。

不同方案怎么在相同环境下比

  • 同一台机器、同一套 build：KDA 要求 baseline 和候选同 ABI、同 build 路径
  • 同样的输入：固定 shape 和 dtype，最好用生产 shape
  • 交替或随机先后：KDA 让 A/B 交替跑；CUDA-L1 每轮随机决定 reference 和 candidate 谁先跑
  • 离群值复测：CUDA-L1 把超过 3x 的结果放到第二张 GPU 上复测，相差 10% 以内才接受
  • Baseline 要强：对比 torch.compile，FP32 开 TF32，有厂商库就比厂商库

比的是 agent 方案而不是 kernel 时，还要固定 model 版本、image 和 seed，各方案跑同一批题（见 大批量跑 agent）。

必答点

  • kernel 是异步执行的，所以用 CUDA event，或在计时前后 synchronize
  • warmup，多次取 median，清 L2，锁时钟，独占 GPU
  • 单次运行调到 1–15 ms，或用 CUDA graph 去掉 launch overhead
  • 相同环境：同机器、同 build、同输入，交替或随机先后
  • baseline 要强：torch.compile、TF32、厂商库
  • 比 speed of light 还快的结果是 bug

追问

论文里的 speedup 能直接比吗？

不能。baseline、精度、硬件、shape 和 best-of-k 的选法都不一样。robust-kbench 剔除受污染的题后，3.13x 只剩 1.49x。

结果怎么报告？

报 geomean speedup 和 fast_p。同时写清 hardware、dtype、PyTorch 版本，以及 best-of-k 是怎么选的。

agent 把计时函数改了怎么办？

harness 放在 agent 写不到的进程或文件里，CUDA Agent 用文件权限保护 verify 和 profile 脚本（见 sandbox）。别的钻法见 reward hacking。

FlashVector 在这方面写了什么？

baseline 和候选在同一环境测，config sweep 跑在生产机型的隔离节点上。warmup 几次、是否锁 GPU 时钟、是否清 L2，论文没写。

单个 kernel 测准了，就能说线上快了吗？

不能。端到端有自己的 noise floor（见 noise floor），kernel 的提升也常常传不到端到端（见 局部和端到端）。

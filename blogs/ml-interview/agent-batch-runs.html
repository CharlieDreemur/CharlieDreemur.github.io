5000 个 task 一夜跑完：
怎么大批量、可比较地跑 agent？

先弄清楚：每个概念是什么

Run
agent 把一个 task 从头做到尾的一次执行，里面有很多次 model call 和 tool call。
Queue 和 worker
task 先排进 queue，worker 一个个取走去跑。像取号机和柜台，开几个柜台就是几个并发。
Rate limit
模型 API 每分钟允许的请求数和 token 数，超了返回 429。常用 token bucket 守住它，桶里按固定速度补令牌，发请求先拿令牌，拿不到就等。
断点续跑
每个 task 跑完就写一条结果。进程挂了重启时，跳过已经有结果的 task。
可比较
两个方案的分数能直接相减的前提。model 版本、image、seed 和 task 列表都一样，只有被比较的那一处不同。

30 秒回答

I'd start with the arithmetic. 5,000 tasks in eight hours is about ten per minute, so if each run takes fifteen minutes I need roughly 160 running in parallel. Tasks go into a queue, and each worker pulls one and runs it in its own sandbox, so runs don't share state. The real bottleneck is usually the model API's rate limit, so I throttle with a token bucket and retry with backoff. Every finished task writes one result row, so a crash resumes instead of restarting. And I pin the model version, the environment image and the task list, so every variant runs under the same conditions.

先算账

先算要多少并发，再谈架构。一夜按 8 小时算，也就是 480 分钟。5000 ÷ 480 ≈ 每分钟 10.4 个 task。每个 run 按 15 分钟算，10.4 × 15 ≈ 160 个并发。15 分钟是假设，面试时先问面试官。顺序跑要 5000 × 15 分钟 = 1250 小时，约 52 天。

再算 rate limit。假设每个 run 用 20 万 token，5000 个 run 一共 10 亿 token，平摊到 480 分钟约每分钟 208 万 token。API 的额度低于这个数时，瓶颈是 rate limit，加机器没有用。

Version chain

版本做法还剩的问题
v1 一个 loop一个 task 接一个 task 顺序跑要 52 天
v2 Queue + workertask 进 queue；约 160 个 worker，每个起自己的 sandbox，跑完销毁API 返回 429；一个进程挂了，整批重来
v3 Rate limit + 断点续跑用 token bucket 守住 rate limit，失败后退避重试；每个 task 写一条结果，重启时跳过已完成的两个方案的分数不能直接比
v4 可比较固定 model 版本、image、seed；各方案跑同一批 task要在 GPU 上计时的 task 互相干扰
v5 GPU 排队（推断）编译和正确性检查并发跑；计时独占一张 GPU，排队跑GPU 数量决定计时这一步的总时长

v5 是推断。中文样本里没有一条把 GPU 调度和 agent 连在一起问。依据是 kernel agent 的 task 要在 GPU 上计时，两个 run 同时用一张卡，时间就不准。

sandbox 怎么隔离见 sandbox 和 verifier 隔离。哪些错误该重试、checkpoint 怎么存见 tool 失败与重试。

必答点

  • task 进 queue，每个 worker 起自己的 sandbox，不共享状态
  • 瓶颈常是模型 API 的 rate limit，用 token bucket 守住它，失败后退避重试

  • 固定 model 版本、image、seed，各方案跑同一批 task
  • 要在 GPU 上计时的 task，编译可以并发，计时独占 GPU（推断）

追问

为什么要限制 agent 的并发数？

模型 API 的 rate limit 和机器的 CPU、memory 都有上限。并发超过上限后请求大面积失败，重试又把负载推得更高。百度 Agent 岗的面经里有这道原题。

有的 run 卡住不结束，怎么办？

每个 run 设 timeout 和步数上限。超时就记成失败并写进结果，把 worker 让出来（见 tool 失败与重试）。

怎么保证不同方案是在相同环境下比较？

固定 model 版本、image、seed 和 task 列表。FlashVector 也要求 baseline 和候选在同一个环境里测。差多少才算数见 noise floor。

结果文件里每条记什么？

task id、方案版本、成功与否、步数、token、latency 和 trace 的路径。有了这些，失败的 run 才能按类型统计（见 observability）。

GPU 不够，计时排不完，怎么办？

这一条是推断。只让通过了编译和正确性检查的候选去排队计时，CUDA Agent 也是把 CPU 上的编译和 GPU 上的测量分开（见 怎么公平地 benchmark）。

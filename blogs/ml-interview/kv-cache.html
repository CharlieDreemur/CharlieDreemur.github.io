KV cache 缓存什么？为什么能加速？
占多少显存？

英文问法What is the KV cache and why does it speed up generation? · How much memory does it take? · Prefill vs. decode? · Implement a decoder KV cache.

考过面经：NVIDIA MLE 电面 2026 的 ML coding 就是实现 KV cache（1p3a 1184818）；NVIDIA 一亩三分地题库有 "Implement a Decoder KV Cache"

先弄清楚：每个概念是什么

Autoregressive decode
一次只生成 1 个 token，拼回输入再生成下一个。像一个字一个字写作文，每写一个字都要回头看前面所有字。
KV cache
causal mask 下，前面 token 的 K、V 不会因为后面的 token 改变，就存起来下一步直接用，像把算好的中间结果记在草稿纸上。Q 只用当前这一个，所以不存。例：生成第 101 个 token 时，前 100 个的 K、V 从 cache 读，只为第 101 个算 q、k、v。
Prefill
把整个 prompt 一次并行 forward，算出所有 K、V 填进 cache，并给出第一个输出 token。矩阵乘很大，算力是瓶颈（compute-bound）。
Decode
之后每步只处理 1 个新 token，却要把全部 weights 和整个 cache 从显存读一遍。算得少、读得多，带宽是瓶颈（memory-bound）。
显存代价
cache 随 context 长度和 batch 线性增长，长 context、大 batch 时比 weights 还大。

30 秒回答

With a causal mask, the keys and values of earlier tokens never change, so each layer caches them. Each decoding step computes q, k and v only for the new token, appends k and v, and attends one query over all cached keys: O(n·d) per layer instead of re-running the whole prefix. Prefill processes the prompt in parallel to fill the cache and is compute-bound; decode handles one token per step and is memory-bound. The price is memory: 2 × layers × KV heads × head dim × bytes per token, times length and batch, which can exceed the weights. GQA, paging and quantization reduce it.

关键公式与手算

\[ \text{KV cache} = 2 \cdot L \cdot n_{kv} \cdot d_{head} \cdot \text{bytes} \cdot T \cdot B \]

2 = K 和 V；\(L\) 层，\(n_{kv}\) 个 KV head，context 长度 \(T\)，batch \(B\)。

LLaMA 2 7B（32 层，\(d = 4096\)，MHA，fp16）：

  • 每 token：2 × 32 × 4096 × 2 bytes = 512 KiB
  • \(T = 4096\)：一条序列 2 GiB；\(B = 32\)：64 GiB，约是 weights（6.7B × 2 bytes ≈ 13.4 GB）的 5 倍
  • 换成 GQA 的 8 个 KV head（LLaMA 3 8B）：每 token 128 KiB，小 4 倍，见 MQA、GQA、MLA

省了多少计算：decode 第 \(t\) 步每层，有 cache 是 \(O(td + d^2)\)；没有 cache 要把整个前缀重新 forward，\(O(t^2d + td^2)\)。推导见 Transformer 复杂度。

手撕 KV cache（NumPy，单层单 head）

class KVCache:
    def __init__(self, max_len, d):
        self.K = np.zeros((max_len, d))   # 预分配，不每步拷贝
        self.V = np.zeros((max_len, d))
        self.t = 0                        # 已缓存几个 token

    def step(self, x, Wq, Wk, Wv):
        # x: (d,) 新 token；只为它算 q、k、v
        q, k, v = x @ Wq, x @ Wk, x @ Wv
        self.K[self.t], self.V[self.t] = k, v
        self.t += 1
        K, V = self.K[:self.t], self.V[:self.t]
        s = K @ q / np.sqrt(q.size)       # 1 个 query 对 t 个 key
        p = np.exp(s - s.max())
        return (p / p.sum()) @ V

逐个 token 调 step 的输出和一次算完整的 causal attention 相同。真实的 prefill 一次写入整段 prompt 的 K、V。多层就每层一个 cache。

必答点

  • 缓存每层前面 token 的 K、V，不存 Q：causal 下它们不会变
  • 每步只为新 token 算 q、k、v，1 个 query 对 \(t\) 个 key，每层 \(O(td)\)
  • prefill 并行、compute-bound；decode 逐 token、memory-bound
  • 显存 \(= 2\cdot L\cdot n_{kv}\cdot d_{head}\cdot \text{bytes}\cdot T\cdot B\)，long context 的主要瓶颈
  • 缩小：MQA / GQA / MLA、PagedAttention、KV cache quantization

追问

为什么不缓存 Q？

每步的输出只需要当前 token 的 q；以前 token 的 q 只用来算它们自己的输出，早就算完了。

用了 RoPE，cache 里存的是转之前还是转之后的 k？

转之后的。k 的位置在写入时就定了，以后不用再转。DeepSeek-V2 的 MLA 也是把带 RoPE 的那部分 key 直接缓存。

PagedAttention 解决什么问题？

以前的系统按最大长度给每个请求预留一整块连续显存，只有 20.4%–38.2% 真正存了 token 的 K、V。vLLM 按固定大小的 block 分页管理，浪费接近 0，throughput 提升 2–4 倍。

KV cache 最大能到多少？

Pope et al.：500B+ 的 MHA 模型，batch 512、context 2048 时 KV cache 共 3 TB，是 weights 的 3 倍。batch 和长度大到这个程度，每步读 cache 的时间超过读 weights。

还有什么办法省？

减 KV head（MQA、GQA、MLA）；KV cache quantization（DeepSeek-V2 平均每个元素 6 bits）；多个请求共用同一段 prompt 前缀的 cache；只保留最近一段窗口的 K、V（sliding window）。

Siri 调完 tool 之后，怎么生成 grounded 的回答？
怎么 eval？

英文问法Design a Siri response-generation flow for an assistant that calls tools and then speaks a concise answer. · How do you evaluate factuality, usefulness, and length for a voice answer? · Why does hallucination happen, and which guardrails reduce it?

考过Apple Siri MLE 全职 2026-03 的 case study（"case study on response evaluation and LLM challenges"，1p3a 1170553 AI 摘要）· 第一句英文问法是一亩三分地站方题面的原文 · 这是同产品方向最接近的真题，但不是 Agentic Search 组问的

先弄清楚：每个概念是什么

Grounding
回答里的每句话都能在 tool result 里找到依据，像写报告时每个数字都有出处。
Source of truth
tool result 说了算，模型自己的记忆不算。时间、金额、ID 这类字段直接 copy，不让模型重写。例：tool 返回 3:00 PM，回答说“4 点”，这就是错。
Claim
回答里一条可以单独核对的事实。例：“UA 123 明天 3 点起飞”有两条 claim：航班号、起飞时间。
Abstention
没查到就说没查到。空结果和调用失败要分开。前者说“没查到”，后者重试或如实说出错了。
Voice length budget
语音回答要短，因为听的人不能回看。先说答案，列表只念前几项。

30 秒回答

I'd split it into five stages: run the tools, select the evidence, generate the answer, verify it, and format it for speech. The tool result is the source of truth, so critical fields like times and IDs are copied, not generated. I'd evaluate claim-level groundedness, required-field recall, correct abstention, and spoken length, on a golden set plus adversarial cases, then check reformulation and barge-in online.

五个 stage

Stage做什么防什么
Tool execution返回 typed result，区分空结果和调用失败把失败当成“没有”
Evidence selection按问题选字段；按 record 截断，不拦腰切context 过长、丢关键字段
Generation只依据 evidence；不够就追问或说找不到模型用自己的记忆补内容
Verification每条 claim 对 evidence 核对；时间、金额、ID 做 exact match细节出错
Voice formatting先说答案，数字转成口语太长、读出来别扭

Hallucination 分六类：contradiction（和 tool 矛盾）、unsupported（tool 没给却说了）、entity confusion（张冠李戴）、temporal（时间解析错或用了旧数据）、omission（为了短漏掉必要信息）、该拒答却答。

Eval 指标

维度Metric
Factualityclaim precision = 有依据的 claim ÷ 全部 claim；关键字段 exact match
Completenessrequired-field recall = 答到的必要信息 ÷ 全部必要信息
Abstentionunanswerable 的拒答率和 answerable 的回答率，一起看
Usefulness人工或 LLM judge 按 rubric 打分，judge 用人工校准
Voice在长度预算内的比例
Onlinereformulation（换个说法再问）、barge-in（打断）、task completion

例：回答有 4 条 claim，3 条有依据 → claim precision 0.75。这类问题要求答 3 项信息，答到 2 项 → required-field recall 0.67。

必答点

  • 五个 stage 分开，每个 stage 单独可测
  • tool result 是 source of truth；关键字段 copy，不生成
  • claim-level 的 precision 和 required-field recall 一起看
  • abstention 单独统计；空结果和调用失败分开处理
  • 数据：golden set 加 adversarial（空结果、结果矛盾、payload 截断、context 变长）

追问

回答变短之后漏信息怎么办？

按 intent 定 required fields，先保 required-field recall，再压长度。两个 metric 一起看，只压长度会把 omission 推高。

context 变长后质量下降怎么办？

先量：画 context 长度和 claim precision 的曲线。再治：旧 tool result 压成 summary，名字、ID、日期逐字保留。只把和当前问题有关的字段放进 context。

verifier 也是 LLM，不可靠怎么办？

关键字段用规则校验，其余抽样做人工校准，多堆几个 judge 帮助有限（见标注与 LLM judge）。

“没查到”和“tool 失败”怎么区分？

tool 返回里带状态：成功但 0 条、失败（超时、权限）。失败要重试或如实告知；确实 0 条才说找不到，并说明查了哪些 source。

为什么会 hallucinate？

四个主要原因：模型的 parametric memory 压过 context。context 长、干扰多。payload 被截断，模型补全了缺的部分。训练时偏向“总要给个答案”。更一般的原因和对策见 LLM hallucination。

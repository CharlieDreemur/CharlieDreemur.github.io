怎么防 reward hacking？

先弄清楚：每个概念是什么

Reward hacking
agent 让分数变高，但没有完成任务。例：评测说 kernel 又对又快，其实它没算，或者算的那部分没被计时。
Harness
判定候选对不对、测它多快的那段代码。agent 的去留和 reward 全靠它，所以它就是被攻击的对象（见 LLM harness）。
Caching allocator
PyTorch 释放的显存不还给系统，下一次申请时直接复用，里面的旧数据还在。
CUDA stream
GPU 上的一条任务队列。计时只等 default stream 时，放到别的 stream 上的计算不算进时间。
Speed of light（SOL）
按硬件峰值算出来的时间下限。比它还快的结果一定有问题。

30 秒回答

Reward hacking is when the agent raises its score without doing the task. In kernel work there are three well-known cases. Sakana's system found a memory exploit in its own harness, and one kernel reported as 150x faster was actually 3x slower. A third of CUDA-L1's kernels ran work on a side stream the timer missed. METR saw o3 overwrite the grader's timer. So I treat the harness as the attack surface: run each candidate in its own process, keep the scripts read-only, re-verify inside the timing loop, reject anything faster than the hardware limit, and audit sudden jumps by hand.

常见类型和三层防御

常见的类型有调用 PyTorch fallback、缓存输出、降精度、hardcode 测试 shape 和改评测脚本。SOL-ExecBench 的统计里有 14.5% 的提交被标为 hack，其中最多的是降精度。

  1. 隔离 harness：candidate 分进程跑，输入每次 clone，计时等所有 stream，评测脚本只读。隔离用什么技术见 sandbox 和 verifier 隔离
  2. 规则和物理上限：运行时禁止 PyTorch fallback；计时循环里每次重新校验输出；比 SOL 还快的结果直接作废
  3. Judge 加人工：reward 突然跳高就让 LLM judge 复查，高分样本人工抽查，发现的手法固化成新规则

KernelGuard 用静态规则、physics floor 和 LLM judge 三层，把比赛里的 hacked 提交率从 3.45% 降到 0.37%。Search agent 一侧的 reward hacking 见 search agent 怎么训。

必答点

  • 定义：分数高了，任务没完成
  • 三个例子：Sakana 的 memory exploit、CUDA-L1 的 stream、METR 的 o3 改 timer
  • 搜索或 RL 越强，越容易找到 harness 的漏洞
  • 第一层是隔离：分进程、clone 输入、等所有 stream、脚本只读
  • 第二层是规则和 SOL，第三层是 judge 加人工抽查高分
  • 在 prompt 里写“不要作弊”没有用

追问

在 prompt 里写“不要作弊”为什么不行？

METR 试过，效果很小。事后问 o3 这样做是否符合用户的意图，10 次里它 10 次回答 no，说明它知道这是作弊。所以只能靠 harness 拦。

Speed of light 怎么算？

用运算量除以硬件的峰值算力。4096 × 4096 的 matmul 是 \(2 \times 4096^3 \approx 1.37 \times 10^{11}\) FLOPs，H100 的 BF16 峰值约 989 TFLOPS，相除约 0.14 ms。KernelBench v0.1 给的下界是约 0.138 ms。

让 agent 自己写 test 行不行？

不行。Meta 的 KernelFalcon 让 LLM 生成 test harness，原文把这一点列为弱点。判定要由 agent 改不了的代码做。

降精度算不算 hack？

容差太宽时它能过检查，实际是用 FP16 或 TF32 算完再转回来。SOL-ExecBench 里这一类占全部提交的 6.4%。对策是按 dtype 设容差，见怎么验证 kernel 正确。

你自己的经验怎么接上？

RL environment 里的 verifier 就是这里的 harness。原则是它的覆盖面要大于 policy 的搜索能力，并且持续找人或 agent 来攻击它。只讲简历上公开的层面。

怎么证明 agentic search 比普通 search 好？

英文问法How would you show the agentic experience beats the same retrieval system behind a conventional search interface? · Where does an agent add value, and where is deterministic search enough?

考过Walmart Labs MLE onsite 原题 Design an Agentic Search Experience 的追问（PracHub，编辑版，英文问法是该页的转述）· Agentic Search 评测组 JD 写 "offline and online metrics"（200670397）· 这个组是否这样问是推断

先弄清楚：每个概念是什么

Baseline
同一个 retrieval 系统，放在普通 search 界面后面：返回结果列表，不生成答案，也不多步搜索。
Ablation
一次只改一样东西。只加“生成答案”，只加“多步”，分别看各自带来多少增量。
Slice
按 query 类型分组看结果。平均数会把差异盖住，因为 agent 的优势应该集中在某几类 query 上。
Guardrail metric
不能变差的指标，比如 latency、cost、错误回答率。主指标涨了，guardrail 破了，也不能上线。
A/B test
线上把用户随机分成两组，一组用新版，一组用旧版，比较行为指标。

30 秒回答

I'd hold the retrieval system fixed and compare the two interfaces, so the difference is the agent, not the index. Offline, I'd run both on the same queries, sliced by type: simple lookup, multi-hop, aggregate, and unanswerable. I expect the agent to win on multi-hop and aggregate and tie on simple lookups, and I need to check it doesn't lose on unanswerable ones by making things up. I'd report task success together with latency and cost. Online, I'd run an A/B test on signals like reformulation rate, with guardrails on latency and wrong answers. If it only wins on some slices, I'd route only those to the agent.

按 slice 看

Slice预期重点看
Simple lookup持平latency 和 cost 不能明显变差
Multi-hopagent 赢task success、per-hop recall
Aggregate、temporalagent 赢答案正确率
Unanswerable风险最大错误回答率、abstention rate

公平比较：同一个 index、同一批 query、配对检验（见 offline eval）。两种界面的原生指标不同，一个是结果列表，一个是答案，所以要统一到任务层面，看这个问题有没有被正确解决，用户花了多少步。

必答点

  • 固定 retrieval，只换界面，差异才能归因到 agent
  • 按 slice 看，不只看平均
  • 质量和 latency、cost 一起报
  • unanswerable 是 agent 最容易输的地方
  • 只在赢的 slice 上用 agent：router 分流

追问

一个返回列表，一个返回答案，指标不一样怎么比？

统一成 task success。对普通 search：gold 文档在前 k 条里，就算用户能自己找到答案。对 agent：答案正确并且有依据。再加一个用户成本的指标，比如到拿到答案为止的操作步数。

agent 质量更好，但慢很多、贵很多，怎么办？

不做全量替换。前面加一个 router 判断 query 类型，简单 lookup 走普通 search，多跳和聚合类才走 agent。router 自己也要评，看分错的代价是多少。

online 看什么指标？

主指标：reformulation rate、放弃率、是否还要点开原始结果。guardrail：p95 latency、用户举报的错误回答。

A/B 刚上线时新版指标很好，过两周回落，为什么？

novelty effect：用户对新界面好奇，多用了几次。实验要跑到指标稳定，看稳定之后的数。

agent 在哪些地方其实没有价值？

一次检索就能答的问题。这时多步只增加 latency 和出错机会。能用确定性的代码解决的步骤，也不要交给模型。

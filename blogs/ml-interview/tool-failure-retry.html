先弄清楚：每个概念是什么

Transient error
等一下再发可能就好的错误。例：timeout、rate limit（HTTP 429）、网络抖动。
确定性错误
同一个调用再发多少次，结果都一样的错误。例：参数错、文件不存在、权限不够。
幂等（idempotent）
同一个调用执行一次和执行多次，效果相同。例：把文件内容设成 X 是幂等的，往文件末尾追加一行不是。
Exponential backoff
每次重试前等的时间翻倍，并且有次数上限。像打电话占线，隔一会儿再拨，越拨间隔越长。
Checkpoint
每一步之后把当前状态落盘，像游戏存档。崩了就从最近的存档接着玩。

30 秒回答

I split errors into three kinds. Transient ones, like timeouts and rate limits, are retried by the harness with exponential backoff and a cap, without involving the model. Deterministic ones, like a bad argument or a missing file, go back to the model as the tool result so it can fix the call. Calls with side effects are retried only if they're idempotent; otherwise I check the state first. To prevent loops, the harness stops and escalates when the same call keeps failing. And it checkpoints messages and task state after every step, so a crashed run resumes from the last step instead of starting over.

三类错误，各自谁处理

错误类型例子谁处理怎么处理
Transient errortimeout、rate limit、网络抖动harness自动重试，用 exponential backoff，有次数上限。超过上限才把报错交给 model
确定性错误参数错、文件不存在、权限不够model报错原样当作 tool result 还给 model，让它改调用
有副作用的调用写数据库、开 PR、发通知harness 先把关幂等才重试。不幂等就先查状态，确认上一次没生效再发

所以“程序判断还是交给 model”的回答是两者分工。从错误码就能看出来的，由程序判断。要理解任务才能改对的，交给 model。

Exponential backoff 手算一遍，数字是举例。第一次重试前等 1 s，之后每次翻倍，最多重试 3 次，最坏情况一共等 \(1 + 2 + 4 = 7\) s。假设每次调用独立地有 5% 的概率遇到 transient error，连着 4 次都失败的概率是 \(0.05^4 \approx 6 \times 10^{-6}\)。

防死循环和 checkpoint

防死循环。model 可能反复发同一个失败的调用。harness 给每次调用的 tool 名和参数算一个 hash，同一个 hash 连续失败 N 次就停下并上报。相同的 action 反复出现也这样处理。最后用 max steps 兜底。stop condition 的一般讲法见 search loop。

Checkpoint。每一步之后，harness 把 messages 和 task 状态落盘，里面带上 step 编号和最后一个 tool call 的结果或报错。进程挂了，重启后先读最近的 checkpoint，再从下一步接着跑。最后那一步可能只执行了一半，恢复时把它按有副作用的调用处理。

必答点

  • 错误分三类：transient error、确定性错误、有副作用的调用
  • transient error 由 harness 自动重试，exponential backoff，有上限
  • 确定性错误当作 tool result 还给 model，让它改
  • 有副作用的调用幂等才重试，否则先查状态
  • 防死循环：同一个调用连续失败 N 次就停下上报，加 max steps
  • checkpoint：每步之后把 messages 和 task 状态落盘

追问

tool 调用失败后 model 开始编造结果，怎么办？（蚂蚁原题）

没有成功的 tool result，verifier 就不放行。结果只认 tool 的真实输出，不认 model 的转述。

Task DAG 里 B、C、D 并行，D 崩了怎么恢复？（字节，作者转述）

每个节点的结果单独落盘。只重跑 D，B 和 C 的结果直接读回来，E 等 D 完成再开始。

上游 LLM API 一直返回 429 怎么办？（Qualified Health，转述）

只靠每个 worker 自己 backoff 不够。在调度层用 token bucket 限流，再加 backpressure，也就是上游忙的时候少派任务（见 大批量跑 agent）。

一个 timeout 的调用，到底执行了没有？

不知道。所以有副作用的调用要带一个 idempotency key 让对方去重，或者重试前先查状态。

让 model 参与错误分析和恢复，行不行？（影石创新原题）

行，确定性错误本来就交给它。transient error 不交给它，因为等一下重发就能好，交给 model 只是多花 token。

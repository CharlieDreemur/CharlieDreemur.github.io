Bit-exact 训练要保证什么？
nondeterminism 从哪来，为什么值得付 overhead？

英文问法What does bitwise-deterministic training mean, and where does nondeterminism come from? · How would you check that two training runs are bit-exact? · Why pay a step-time overhead for determinism?

考过推断，没有面经问过，依据是团队的 determinism tracker 和官方 blog。

先弄清楚：每个概念是什么

Bitwise determinism
两次 run 每一步的结果每个 bit 都相同，不是 loss 看起来差不多。
Fixed environment
保证的前提是 model、data、seed、software、hardware class 和 topology 都相同。换了卡数或并行配置就不在保证里。
Reduction order
很多数相加时先加谁后加谁。浮点加法每一步都要舍入，顺序一变末位就可能变。ring 和 tree 的次序见 all-reduce。
Autotuning
运行时试几种 kernel 配置，挑最快的用。两次挑的不一样，bit 就可能不一样。

30 秒回答

Bitwise determinism means two runs in the same fixed environment, with the same model, data, seed, software, hardware and topology, produce identical bits at every step, and a resumed run matches the uninterrupted one. Nondeterminism comes from floating-point reduction order and from autotuning that picks different kernels. There are three gates: repeatability, baseline equivalence and restart replay. You verify with tensor hashes, not printed loss. It's worth the cost because you cannot bisect a divergence you cannot reproduce. With determinism you replay a loss spike and change one thing at a time. It does cost step time, and the team keeps driving that cost down.

怎么验证：三个 gate

  1. Fixed-environment repeatability：同一个 fixed environment 跑两次，training metrics 和 trace event 要 bit-exact
  2. Baseline equivalence：一个优化自己可重复还不够，还要和已有的 deterministic baseline 比
  3. Restart replay：从 checkpoint 恢复的 run，要和不中断的 run 从那一步起一致

打印的 loss 不够灵敏，两次 run 的 loss 一样时 gradient 的低位仍可能不同。做法是每步给选定的 metric 和 tensor 算 fingerprint（torch.hash_tensor），最后逐 byte 比较。

为什么值得付 overhead

  • Debug：复现不了的 divergence 没法二分定位。loss spike 能在同一步重现，才能一次只换一个组件来查
  • RL：training 和 generation 可以用不同的 EP size。同一层 MoE 在两种 EP size 下的输出只差末位，但到 sampled token 的 log-prob 上就差得明显。修法是一个 opt-in 的 flag，让每个 EP size 走同一棵 fp32 reduction tree。这比 fixed environment 的保证更强

deterministic mode 会拖慢 step time，团队一直在把这个 overhead 往下压。

必答点

  • bit-exact 指每一步每个 bit 相同，前提是 fixed environment，topology 也算在内
  • 浮点加法不满足结合律，reduction order 一变末位就变
  • 两类来源：reduction order（比如依赖 topology 的 gradient reduction）和 autotuning
  • 三个 gate：repeatability、baseline equivalence、restart replay
  • 验证看 tensor 的 hash，不看打印的 loss
  • 值得付 overhead，因为复现不了的 divergence 没法二分定位

追问

开了 deterministic 为什么会慢？overhead 怎么压下来？

让并发的 writer 串行能恢复 determinism，但丢了并行度。改成 private slot 后 kernel 内部照样并行。另一处是 fill_uninitialized_memory，它给未初始化的内存填值。关掉后结果仍然 bit-exact，steady-state 性能明显变好。

小规模没问题，大规模才出现 nondeterminism，怎么查？

问题通常出在随规模变的 communication 或 expert-parallel 路径上。做法是逐步加规模，trace 选定的 rank，找到第一个随规模变的 operation。每个 rank 按顺序记下 tensor fingerprint，离线比较。

deterministic mode 下有什么不能用？

--deterministic-mode 会设好环境、打开 PyTorch 的 deterministic algorithms，并拒绝没有 deterministic 路径的功能。--moe-router-fusion 自己可重复，但会改变已有的 deterministic baseline，所以还不算保持 baseline 的优化。

Bit-exact 训练要保证什么？
nondeterminism 从哪来，为什么值得付 overhead？

英文问法What does bitwise-deterministic training mean, and where does nondeterminism come from? · How would you check that two training runs are bit-exact? · Why pay a step-time overhead for determinism?

考过推断，非面经，没有一条面经问过这页的内容 · 依据是团队自己的材料：determinism tracker #5785、core 0.20.0 release notes（把它列为 multi-release effort，并链接到官方 blog）、官方 blog（2026-10-06）· tracker 还开着，状态会变

先弄清楚：每个概念是什么

Bitwise determinism
两次 run 每一步的结果每个 bit 都相同，不是 loss 看起来差不多。官方 blog 给了两条保证：独立跑两次每步 bitwise 相同；存取 checkpoint 之后和不中断的 run 相同。
Fixed environment
保证的前提。tracker 要求 model、data、seed、software、hardware class 和 topology 都相同。换了卡数或并行配置，不在这个保证里。
Reduction order
很多数相加时先加谁后加谁。浮点加法每一步都要舍入，顺序一变末位就可能变。FP32 里 16777216 + 1 还是 16777216，所以 (a + 1) + 1 和 a + (1 + 1) 不相等。
Autotuning
运行时试几种 kernel 配置，挑最快的用。两次挑的不一样，算出来的 bit 就可能不一样。
Determinism overhead
开 deterministic 之后 step time 多出来的比例，blog 也叫 determinism tax。

30 秒回答

Bitwise determinism means two runs in the same fixed environment, with the same model, data, seed, software, hardware and topology, produce identical bits at every step, and a run resumed from a checkpoint matches the uninterrupted one. Nondeterminism comes from floating-point reduction order, because every addition rounds, and from autotuning that picks different kernels. Megatron's tracker has three gates: repeatability, equivalence to a deterministic baseline, and restart replay. You verify with tensor hashes, not printed loss. It's worth the cost because you can replay a loss spike and change one thing at a time. The target is under ten percent step-time overhead; NVIDIA's blog reports about two percent on Nemotron.

怎么验证：三个 gate

  1. Fixed-environment repeatability：同一个 fixed environment 跑两次，training metrics 和 trace event 要 bit-exact
  2. Baseline equivalence：一个优化自己可重复还不够，还要和已有的 deterministic baseline 比
  3. Restart replay：从 checkpoint 恢复的 run，要和不中断的 run 从那一步起一致

打印出来的 loss 不够灵敏。两次 run 可以打印同样的 loss，gradient 的低位却不同。blog 的做法是每步给选定的 metric 和 tensor 算 fingerprint，用 torch.hash_tensor，最后逐 byte 比较来确认。PR 模板还要求改 GPU kernel 的 PR 带上 bit-exact determinism test。

为什么值得付 overhead

  • Debug：loss spike 能在同一步重现，再一次只换一个组件来定位（blog）
  • RL：training 和 generation 可以用不同的 EP size，PR #8261 举的例子是 EP8 训练、EP4 生成。它在 Nemotron-3-Nano 上量到一层 MoE 在 EP2 和 EP1 之间有 98% 的 token 不同，每个元素差约 1 ulp；EP2 训练、EP1 生成时 sampled token 的 log-prob 最多差 0.89。修法是一个 opt-in 的 flag，让每个 EP size 走同一棵 fp32 reduction tree

RL 这条比 fixed environment 的保证更强，因为它要跨 EP size 一致。

tracker 的目标是 "less than 10% steady-state step-time overhead"，stretch 目标约 5%。blog 的实测是 Nemotron 3 Ultra 从约 17% 降到 2%，在 3,072 GPU 上是 1.5%。另一个大规模 Nemotron recipe 在 2,432 GPU 上约 2%，800 步内保持 bitwise 一致。blog 的算例是 100 天、10,000 GPU 的训练，overhead 从 15% 降到 5% 省 10 天，也就是 100,000 GPU-days。

必答点

  • bit-exact 指每一步每个 bit 相同，前提是 fixed environment，topology 也算在内
  • 浮点加法不满足结合律，reduction order 一变末位就变
  • tracker 记的两类来源：依赖 topology 的 gradient reduction，Triton autotuning
  • 三个 gate：repeatability、baseline equivalence、restart replay
  • 验证看 tensor 的 hash，不看打印的 loss
  • 目标 overhead 低于 10%，stretch 约 5%；blog 在 Nemotron 上报约 2%

追问

换一种 all-reduce 的 topology，结果为什么会差一个 bit？

ring 沿着环挨个加，tree 两两加，加法次序不同（见 all-reduce）。卡数一变，次序也跟着变。tracker 的第一个 gate 把 topology 列为必须相同的条件。

开了 deterministic 为什么会慢？overhead 怎么压下来？

blog 的例子里，让那几个 writer 串行能恢复 determinism，但丢了并行度。改成每个 N-tile 一个 private slot 之后，kernel 内部照样并行。tracker 另记了一条：关掉 torch.utils.deterministic.fill_uninitialized_memory 后结果仍然 bit-exact，steady-state 性能在两个模型上提高约 16% 和 18%。

低精度训练对 determinism 有什么额外要求？

blog 的表里有一条：load checkpoint 后参数立刻不同，原因是 low-precision 的 weight 或 scale 重建的方式不一样。算 fingerprint 时，MXFP8 和 NVFP4 的 tensor 要把 encoded value 和 scale buffer 都算进去。格式见 MXFP8 和 NVFP4。

小规模没问题，大规模才出现 nondeterminism，怎么查？

blog 的表里有这种情况，原因是随规模变的 communication 或 expert-parallel 路径。做法是逐步加规模，trace 选定的 rank，找到第一个随规模变的 operation。PR #7262 提的 workflow 按 rank 记录有序的 tensor fingerprint，供离线比较。

deterministic mode 下有什么不能用？

--deterministic-mode 会设好环境、打开 PyTorch 的 deterministic algorithms，并拒绝没有 deterministic 路径的功能（blog）。tracker 写 --moe-router-fusion 自己可重复，但会改变已有的 deterministic baseline，所以还不算保持 baseline 的优化。Q4 roadmap 列着 GDN、KDA、QSA、GDP 这几个 kernel 的 deterministic 版本要做。

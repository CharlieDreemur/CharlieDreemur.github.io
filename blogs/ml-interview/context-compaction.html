长任务的 context compaction：
什么时候压，压什么，对 cache 有什么影响？

先弄清楚：每个概念是什么

Context window
model 一次能看的 token 上限。长任务里 messages 越积越多，早晚会满。
Context compaction
把旧的历史换成一段摘要，腾出空间。像交接班时只留一页交接单，不把整本值班日志交给下一班。
大 tool result 落盘
很长的 tool result 写进文件，context 里只留路径和开头几行。例：一次查出几万行日志，context 里只放文件路径和前 20 行。
Prefix cache
两次请求的前缀完全相同时，这段前缀算过的结果可以复用。前缀里改了一处，它后面的部分都要重算。
规则文件
不参与 compaction 的固定内容，每次原样放进 context。硬约束写在这里。

30 秒回答

The harness, not the model, watches token usage and compacts when it crosses a threshold, say eighty percent of the window. Large tool results never stay inline: they go to files, and the context keeps a path and a short preview. The summary keeps the goal, the constraints, the decisions made and the open steps. The raw history stays on disk, so anything the summary dropped can be fetched back. Compaction rewrites the prefix, so the prompt cache misses once afterwards. That's why I compact rarely and keep the system prompt and tool definitions fixed at the front. Hard constraints live in a rules file that is never summarized.

什么时候压，压什么

问题做法
谁触发harness 每轮数 token，过了阈值就压，比如到 window 的 80%（数字是举例）。不靠 model 自己想起来
大 tool result写进文件，context 里只留路径和开头几行
摘要里留什么目标、约束、已做的决定、未完成的步骤
摘要丢了细节原始记录留在磁盘，摘要里带路径，要用时按路径取回
不能丢的约束放进规则文件，逐字保留

单个文件本身就放不进 context 的情况是另一道题，见 文件放不进 context。

对 prefix cache 的影响

Prefix cache 的原理见 KV cache 和 inference cost。Compaction 改写了历史，所以从摘要开始往后的部分会 miss 一次。对策有两条。第一条是少压，一次压到位，不要每轮都改一点。第二条是把 system prompt 和 tool 定义放在最前面，compaction 不动它们。

手算一遍，数字都是举例。window 是 200K，阈值 80% 就是 160K。压之前有固定前缀 10K、旧的历史 135K、最近几轮 20K，合计 165K，过了阈值。把旧的历史压成 5K 的摘要，合计变成 35K。压完后的第一次请求里，10K 的固定前缀命中 cache，后面的 25K 重算。再往后每轮又只需要算新增的部分。

必答点

  • 由 harness 按 token 用量触发，不靠 model 自觉
  • 大 tool result 落盘，context 里只留路径和开头几行
  • 摘要保留目标、约束、已做的决定、未完成的步骤
  • 原始记录留在磁盘，丢了的细节按路径取回
  • Compaction 让 prefix cache miss 一次，所以少压，固定前缀不动
  • 硬约束放规则文件，不参与 compaction

追问

摘要把“不能修改生产配置”写成了“修改生产配置”，怎么办？（蚂蚁原题）

约束不交给摘要，它放在不参与 compaction 的规则文件里，每次逐字放进 context。写进长期 memory 之前，再拿规则文件核对一遍。

旧信息已经被摘要掉了，后面还要用怎么办？（字节，作者转述）

原始记录没有删，还在磁盘上。摘要里留着路径，model 用 read tool 把那一段取回来。

compaction 的触发点是 model 主动，还是 harness 实现？

harness 实现。它每轮都能拿到确切的 token 用量，触发条件写成代码最稳，不依赖 model 记得去做。

被问到 Claude Code 或 Codex 的 compaction 是怎么实现的，怎么答？

FlashVector 怎么控制 context 的大小？

它的 Refine 在 run 结束后 in-place 更新 knowledge base，不往后追加，所以 agent 要带的 memory 有上限（见 knowledge base 和 memory）。

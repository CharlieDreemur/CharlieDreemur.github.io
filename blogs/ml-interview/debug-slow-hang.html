训练慢、GPU utilization 低怎么查？
训练 hang 住怎么查？

英文问法If GPU utilization is low during training, how would you debug and benchmark performance? · Your multi-node job hangs. How do you find out why?

考过面经：NVIDIA SWE 2025-12（"If GPU utilization is low during training, how would you debug and benchmark performance?"，Aced 用户提交）；国内：快手（"hang都有可能因为什么，分别要如何排查"）；其他公司：Tower（"Debug Oscillating GPU Utilization During Training"）

先弄清楚：每个概念是什么

GPU utilization（nvidia-smi）
采样周期里"有任意 kernel 在跑"的时间比例，不是 SM 用满了多少。一个很小的 kernel 一直跑也算 100%。例：一步 400 ms 里 kernel 跑了 280 ms → 显示 70%。
Profiler trace 与 GPU gap
把 CPU 和 GPU 每个 kernel 画在时间线上。GPU 上的空白就是浪费，空白前 CPU 在干什么，瓶颈就在哪。像看监控录像找"工人在等什么"。
Implicit sync
CPU 必须等 GPU 算完才能往下走：.item()、print(cuda_tensor)、.cpu()、依赖 GPU 结果的 if。CPU 没法提前排队，GPU 就出现空白。
Straggler
某一张卡比别人慢（数据更长、降频、网卡有问题），所有卡在下一次 collective 都得等它。
Collective hang
collective 要求所有 rank 都调用、顺序和 shape 一致。像开会必须全员到齐，有一个人走错会议室，其余人就无限期干等。

30 秒回答

For slow training I first quantify step time, throughput and MFU; nvidia-smi utilization only tells whether any kernel is running. Then I profile a few steps with torch.profiler or Nsight Systems and classify the gaps on the GPU timeline: idle at the start of each step means the data loader; many tiny gaps mean CPU launch overhead; gaps after .item() or .cpu() are implicit syncs; long NCCL kernels with nothing beside them are exposed communication. For a hang, I dump every rank's Python stack with py-spy, turn on NCCL_DEBUG=INFO and the flight recorder, and look for the rank that is not in the same collective as the others.

训练 hang：一句话 + 步骤

找出"谁没进同一个 collective"，再看它停在哪一行：

  1. init 就卡住：NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,NET 看 bootstrap 和网卡选择
  2. 训练中卡住：每个 rank py-spy dump --pid PID（加 --native 看 C++ 栈）
  3. flight recorder：TORCH_NCCL_TRACE_BUFFER_SIZE=2000 + TORCH_NCCL_DUMP_ON_TIMEOUT=true，超时时每个 rank dump 最近的 collective，用 fr_trace 找缺席的 rank
  4. 复现时开 TORCH_DISTRIBUTED_DEBUG=DETAIL：检查每次 collective 的类型和 shape 是否一致
  5. 设 init_process_group(timeout=...)（NCCL 默认 10 分钟），让 hang 变成报错退出

常见原因：rank 相关的 if 让 collective 顺序或次数不一致。PP send / recv 不配对。某 rank OOM 退出。网络或 PCIe ACS 有问题。

手算例子

  • 慢：step 400 ms = 计算 240 + 等数据 120 + 露出的 all-reduce 40。nvidia-smi 显示 70%（NCCL kernel 也算"在跑"），真正计算只占 60%。num_workers 0 → 8、pin_memory=True 后等数据消失 → 280 ms，吞吐 ×1.43；剩下 40 ms 交给 nccl-tests 和 overlap 去查。
  • hang：8 卡在 step 1200 卡住。py-spy：rank 1–7 停在 loss.backward() 的 DDP all-reduce，rank 0 停在 save_checkpoint() 里的 all_gather，因为它写在 if rank == 0: 里 → collective 不匹配。修法：所有 rank 都调用，或者挪出 if。

必答点

  • util 只表示"有 kernel 在跑"，要看 step time、MFU 和 trace
  • profile → 找 GPU 空白 → 分类：data、launch、sync、comm、straggler、kernel 本身
  • 控制变量：单卡 / 单机 / 多机，synthetic data，nccl-tests
  • hang：py-spy 每个 rank 的栈 + NCCL_DEBUG + flight recorder → 找没进同一 collective 的 rank
  • 设 timeout，把无限等待变成可诊断的报错

追问

GPU util 100% 就说明跑满了吗？

不是。它只看有没有 kernel 在跑，所以小 kernel、memory-bound kernel，甚至 hang 住时 NCCL kernel 在等对端，都可能显示很高。要看 MFU 或 Nsight Systems 里的 SM 活动。

GPU util 周期性忽高忽低（Tower 题）？

把低谷和代码对齐：每 N 步的 checkpoint / eval，DataLoader 的 buffer 取空再填，或 comm 和计算交替暴露。trace 里看低谷时 CPU 在干什么。

怎么找 straggler？

各 rank 记录 step time；TORCH_NCCL_ENABLE_TIMING=1 记录每个 collective 的耗时。慢的 rank 计算时间长，其他 rank 则在 collective 里等得久。

timeout 之后会发生什么？

NCCL backend 的 watchdog 会异步 abort 这个 collective 并让进程崩溃，因为失败的异步 NCCL 操作可能让后续 CUDA 计算用到坏数据。TORCH_NCCL_ASYNC_ERROR_HANDLING 控制具体怎么 abort。

只在多机 init 时卡住，常见什么原因？

NCCL 选错网卡（用 NCCL_SOCKET_IFNAME 指定）、MASTER_ADDR / 端口不通、防火墙。NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,NET 的日志会显示卡在哪一步。

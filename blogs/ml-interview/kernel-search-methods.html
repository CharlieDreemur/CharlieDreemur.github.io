Iterative refinement、evolutionary search 和 RL
怎么选？

英文问法When would you use iterative refinement, evolutionary search, or RL to optimize kernels? · Why not just let the agent keep refining one kernel? · Is a more complex search always better?

考过推断，非面经。没有 Unity 的面经原题，别家面经里也没有直接问这题的 · 依据是公开文献（KernelBench、AlphaEvolve、Meta KernelEvolve、Kevin、CUDA Agent）· Unity 自己的 FlashVector 用的是最简单的单链循环 · 研究向，可以主动带出来

先弄清楚：每个概念是什么

Iterative refinement
一条链。写一版，看反馈，改一版，一直改同一个 kernel。
Beam search
每一轮只留最好的 K 个候选，再从它们往下改。
Evolutionary search
养一个种群。每轮从里面挑 parent，让 LLM 改出 child，好的放回种群。AlphaEvolve 把种群存在一个 program database 里。
MCTS
把候选排成一棵树，按以往的结果决定下一次展开哪个节点。Meta KernelEvolve 的节点可以继承父节点的历史、参考兄弟节点，或者清空重来。
RL
不在推理时多试，而是把试错的经验训练进模型的参数（算法见 PPO 和 GRPO）。

看图：三种方法的形状

30 秒回答

Refinement is one chain: generate, read the feedback, fix. It's cheap and direct, but it gets stuck on its first idea. Search keeps several candidates alive with beam, evolution or MCTS. It adds diversity without training, so it suits a one-off hot kernel, but it burns tokens and is better at finding holes in the harness. RL bakes the skill into the model, which pays off across many ops, but training is unstable and amplifies hacks. In practice you combine them: RL for the base skill, search at inference. All three need a harness the agent can't game, and FlashVector shipped with just a single chain.

三种方法对比

方法优点和证据风险适合的场景
Iterative
refinement		简单便宜，反馈直接。KernelBench 论文里 DeepSeek-R1 在 L2 的 fast_1 从 36% 升到 72%困在第一个思路里；context 越滚越长已有强模型，想快速出结果
Search多样性高，不用训练。AlphaEvolve 让 Gemini 的训练时间少 1%；KernelEvolve 让 Meta 的 Andromeda 广告模型 inference throughput 提升 60% 以上token 贵，CRFM 的一次实验约 7M，Houmao 约 1.9B；搜得越强，越容易找到 harness 的漏洞一次性优化少数热点 kernel
RL能力训进模型，op 多时每次推理便宜。CUDA Agent 对 torch.compile 的 faster rate 是 96.8%，同一个 agent loop 里 Opus 4.5 是 66.4%训练不稳，CUDA Agent 最初 17 步就崩；hack 会被放大，CUDA-L1 有 32.8% 的 kernel 钻了计时漏洞要覆盖很多 op，并压低单次推理的成本

怎么选，怎么组合

  1. 先做 refinement 加 profiler feedback，它最便宜
  2. 单链停滞，而且这个 kernel 值得花 token，再上 search
  3. op 很多，推理成本压不下来，再训 RL
  4. 三种可以叠起来用：RL 训基础能力，推理时再 search 和 refinement

单链会困住有一个具体例子，是 Meta KernelAgent 的 matvec。torch.compile 是 2.09 ms。不给硬件反馈、顺序 prompt 8 轮只到 3.20 ms，比 baseline 还慢。用 Nsight Compute 的指标加 4 个并行 worker 跑 8 轮到 1.95 ms。原文的解释是，没有 profiling 时 LLM 一直沿着第一版 kernel 的写法改，没想过换一种切分方式。

三种方法都要一个 agent 骗不了的 harness。没有它，搜索或 RL 越强，学到的作弊越多（见 reward hacking）。搜索的复杂度和进没进生产也没有正相关，四家系统的对照见设计 kernel agent。

必答点

  • refinement：一条链，便宜，会困在第一个思路里
  • search：同时留多个候选，不用训练，token 贵，更会钻漏洞
  • RL：能力进模型，op 多才划算，训练不稳
  • 可以组合：RL 训基础能力，推理时再 search
  • 三种都依赖一个 agent 骗不了的 harness
  • 搜索复杂不等于能上生产，FlashVector 是单链

追问

多花 token 多试，能换来多少？

METR 给每题约 20 美元的预算，8 路并行做 tree-style sampling，共 300 次尝试，平均 speedup 是 1.81x。原 KernelBench 的设置每题不到 1 美元，是 1.05x。METR 自己说提升主要来自 scaffold 和 prompt。

Search 的预算怎么分给不同的 kernel？

用 speed of light 估计每个 kernel 还剩多少提升空间，接近上限的少给。μCUTLASS 论文这样做省了 19–43% 的 token，同时保住至少 95% 的 geomean。

Serial refinement 和 parallel sampling 哪个划算？

Kevin 的论文里 serial refinement 更划算。它训练时两者都用，每题 16 条 trajectory，每条 4 个 refinement step。

RL 论文的数字能直接比吗？

不能。CUDA Agent 批评 Kevin 和 CUDA-L1 在 KernelBench 上既训练又评测。CUDA Agent 自己的评测也还是原 KernelBench 协议，FP32 baseline 没有开 TF32。

FlashVector 为什么不用更强的搜索？

论文没有解释。它每轮随机抽一层，一轮只做一个改动，篇幅都在 verify 和交付上。这一条适合当反问。

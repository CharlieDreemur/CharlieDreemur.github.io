先弄清楚：每个概念是什么

Launch
CPU 让 GPU 跑一个 kernel 的那次调用。CPU 准备好参数、提交命令就返回，不等 kernel 跑完。
Launch overhead
每次 launch 花在 CPU 上的时间，是微秒级，和 kernel 处理多少数据无关。NVIDIA 的博客在 V100 上量过一个 2.9 µs 的小 kernel，每次 launch 后都同步时，每个 kernel 要 9.6 µs。
Launch-bound
kernel 又小又多，GPU 跑完一个要等 CPU 发下一个。像厨师几秒炒完一个菜，但每张单子都要服务员跑一趟送来。
CUDA Graph
把一整串 kernel 和它们的参数录下来，这一步叫 capture。之后一次调用就把整串重放，叫 replay。
Fallback
输入对不上任何录好的 graph 时，退回 eager，一个个 launch。

30 秒回答

Every kernel launch costs the CPU a few microseconds to set up arguments and submit the work. When a model runs many tiny kernels, that overhead dominates and the GPU sits idle waiting for the CPU. A CUDA Graph captures the whole sequence of kernels and their arguments once, then replays it with a single call. It removes launch overhead; it doesn't make any single kernel faster. It needs fixed shapes and fixed memory addresses, with no CPU sync or data-dependent branches inside. With dynamic shapes, I capture one graph per shape bucket, pad inputs up to the bucket, and fall back to eager when nothing matches.

什么时候有用：手算一遍

一次 forward 有 100 个小 kernel，每个在 GPU 上跑 2 µs，每次 launch 要 5 µs（示意）。逐个 launch 时 GPU 每跑完一个都在等下一次 launch，总共约 500 µs，其中 GPU 只忙 200 µs。换成 CUDA Graph 是一次 replay 加 100 × 2 µs，约 205 µs，快约 2.4 倍。每个 kernel 还是 2 µs，省掉的只有 launch overhead。

反过来，每个 kernel 要跑 5 ms 时，5 µs 的 launch 只占 0.1%，用了也看不出差别。benchmark 时把单次运行调到 1–15 ms 是同一个道理（见 kernel benchmark）。

NVIDIA 博客的实测是 V100 上 2.9 µs 的 kernel，连续 launch 时平均每个 3.8 µs，用 CUDA Graph 是 3.4 µs。PyTorch 文档说 replay 跳过的还有 Python 和 C++ 这两层的开销。

流程和限制

  1. Warmup：先用 eager 跑几次
  2. Capture：再跑一次。这次 kernel 不真的执行，只把 kernel 和参数记进 graph
  3. Replay：之后每次只调用一次 replay，整串 kernel 按录下的参数重跑
  4. Fallback：输入的 shape 对不上任何 graph，就退回 eager
限制原因
shape 固定graph 假设每次 replay 里每个 tensor 的 size 和 layout 都不变
内存地址固定每次 replay 读写同一批地址，新输入要先 copy 进 capture 时用的那块 tensor
不能有 CPU 同步.item() 这类要等 GPU 结果的 op 不能出现在 capture 里
不能有依赖数据的分支录下的是一条固定的 kernel 序列，分支走哪边在 capture 时就定死了
多占显存PyTorch 默认给每次 capture 一个 private memory pool

动态 shape 的做法是按 batch size 分桶，每个桶 capture 一个 graph，输入 padding 到桶的大小。比如分 8、16、32 三个桶（示意），batch 11 的请求 padding 到 16，有 5/16 ≈ 31% 的计算是白做的。batch 40 对不上任何桶，就 fallback。shape 变得很频繁时反而更慢，因为要反复 capture，graph 越多显存也占得越多。

必答点

  • launch overhead：每次 launch 在 CPU 上花几微秒，小 kernel 多的时候 GPU 在等 CPU
  • CUDA Graph：capture 一次整串 kernel，之后每次一次 replay
  • 它只去掉 launch overhead，不改单个 kernel 的速度
  • 限制：shape 和内存地址固定，中间不能有 CPU 同步和依赖数据的分支
  • 动态 shape：分桶，每桶一个 graph，输入 padding，对不上就 fallback 到 eager
  • shape 经常变反而更慢：反复 capture，多占显存

追问

launch 的时候 CPU 做了什么？

准备 kernel 的参数，把命令提交给 GPU，然后立刻返回。PyTorch eager 里每个 op 在这之前还要过 Python 和 C++ 的 dispatch，这几层 replay 都跳过。

怎么知道自己是 launch-bound？

在 Nsight Systems 的 timeline 上，kernel 之间有密集的小空隙，GPU 在等 CPU（见 Nsight profiling 和 训练慢怎么查）。

它和 kernel fusion 有什么区别？

CUDA Graph 不改 kernel，kernel 数和每个 kernel 读写 HBM 的量都不变。Kernel fusion 把几个 kernel 合成一个，launch 次数和 memory traffic 一起降。两个可以叠加。

CUDA Graph 和 torch.compile 是什么关系？

torch.compile 的 reduce-overhead 模式把 CUDA Graph 叠在 fusion 之后用（见 torch.compile）。滴滴 AI Infra 算法岗二面 2026-09-30 问过两者的关系。

为什么用了 CUDA Graph 显存占得更多？

PyTorch 默认给每次 capture 一个 private memory pool，graph 和 capture 时创建的 tensor 还活着，它就不释放。分的桶越多，pool 越多。小马智行的实习面问过这一点，出处是 AIInfraGuide 的二手整理。

Generalized Tensor Parallelism（GTP）是什么？
它和 TP、ZeRO-3 差在哪，all-gather 怎么藏？

英文问法What is Generalized Tensor Parallelism in Megatron Core? · How does GTP_remat differ from TP, and from ZeRO-3 on the data-parallel axis? · How does GTP hide the weight all-gather behind compute, and what happens to the weight gradient?

考过推断，非面经。没有任何面经问过 GTP · 依据是团队自己的 GTP 文档（main 分支 2026-11 的版本，开头标着 experimental，要求 TransformerEngine ≥ 2.19）和 core 0.20.0 release notes · 下面的引文和限制都是这一版文档的说法

先弄清楚：每个概念是什么

GTP_remat
把 TP 切完的那片 weight 再切一次，每卡平时只存一小片。GEMM 之前用 all-gather 拼回完整的 TP slice，算完就释放，像合租时把共用的工具借来用完就还。名字里的 remat 来自 rematerialize。
GTP = TP × GTP_remat
文档的公式就是这一行，意思是两刀相乘，原话是 "every rank stores 1/(TP × GTP_remat) of each linear weight"。例：TP = 4、GTP_remat = 8，每卡存每个 weight 的 1/32。
Model-parallel 轴和 data-parallel 轴
ZeRO-3 和 FSDP 沿 DP 的 rank 切 weight（见 DP、ZeRO、FSDP）。GTP_remat 按文档是 "a sub-axis of the weight-parallel grid that sits on top of TP"，和 TP 叠在一起用，外面还可以再套 DP。
Prefetch chain
weight 按 forward 的顺序连成一条链。算当前层时，提前把下一层的 all-gather 发出去。
Deferred finalize
weight gradient 的 reduce-scatter 异步发出，结果推迟一步才并进 main_grad。这里的一步是 backward 往前走一层，不是一个 training step。

30 秒回答

GTP equals TP times GTP_remat. TP keeps each weight split through the GEMM. GTP_remat splits the TP slice again: each rank keeps one shard, rebuilds the full slice with an asynchronous all-gather right before the GEMM, and frees it afterwards. The doc calls it an implementation of ZeRO-3 that shards along a model-parallel axis, not the data-parallel one, and materializes one weight at a time, not a bucket. Each layer's all-gather is prefetched during the previous layer's GEMM, so in an L-layer model L minus one gathers are hidden. Weight gradients go back through an async reduce-scatter whose finalize is deferred one step. It's still experimental.

文档说 "GTP_remat is an implementation of ZeRO-3"，再列出两点区别。第一点是 "It shards along a model-parallel axis, not the data-parallel one."，第二点是 "It materializes one weight at a time, not a bucket."，所以每个 weight 可以单独 prefetch。“TP 切计算、传 activation，GTP_remat 只切存储、传 weight”是我对着这张表读出来的推断，文档没有这句话。TP 本身怎么切见 TP Linear。

手算一遍。h = 8192 的方阵 weight 用 bf16 存是 128 MiB。TP = 4 后每卡 32 MiB。再开 GTP_remat = 8，每卡平时只存 4 MiB，GEMM 前 all-gather 回 32 MiB，算完释放。合起来是 1/32，对应文档的 "32× weight-memory reduction"。同一句里的 "128× wire-bandwidth reduction" 文档没有给推导。

all-gather 和 weight gradient 怎么藏在计算后面

  1. Forward：算第 i − 1 层的 GEMM 时，提前发第 i 层的 all-gather。文档 1.1 节写 "Layer i's AG overlaps with layer i−1's GEMM."，3.1 节写成 \(\text{AG}(W_{i+1}) \parallel \text{GEMM}(W_i)\)。两处下标错开一位，说的是同一件事，本页统一用前一种
  2. 链头：第一层前面没有 GEMM，所以 "For an L-layer model, L−1 all-gathers are fully hidden behind compute."
  3. Cold start："every weight's very first AG is synchronous"，prefetch chain 从第二次 forward 才开始
  4. Backward：反着走，第 i − 1 层的 all-gather 和第 i 层的 dgrad 重叠
  5. Weight gradient：reduce-scatter 异步发出，"Finalization is deferred one step"。backward 走到第 i − 1 层时，先等第 i 层的 reduce-scatter 完成，再把结果加进 main_grad。这样第 i 层的 reduce-scatter 能和第 i − 1 层的 backward GEMM 重叠。链头用同步的 reduce-scatter，"since nothing follows it"

Overlap 的一般做法和 exposed communication 怎么算见 overlap。

必答点

  • GTP = TP × GTP_remat，每卡存每个 linear weight 的 1/(TP × GTP_remat)
  • GTP_remat 是 ZeRO-3 的做法：切开存，用前 all-gather，用完释放，gradient 走 reduce-scatter
  • 和 DP 轴上的 ZeRO-3 有两点区别：切在 model-parallel 轴，一次一个 weight
  • 第 i 层的 all-gather 和第 i − 1 层的 GEMM 重叠，L 层藏住 L − 1 次
  • Weight gradient 用 async reduce-scatter，finalize 推迟一步
  • 状态是 experimental，要求 TransformerEngine ≥ 2.19

追问

GTP_remat 里的各个 rank 算的是同一份数据吗？

不是。文档写默认 "all GTP_remat ranks distribute independent samples"。开了 sequence sharding 后，各 rank 算同一个 microbatch 的不同 sequence 分段。

为什么不直接把 FSDP 的 bucket 缩到一个 weight？

文档的说法是 "FSDP's overlap is bucket-grained by design"，bucket 是为了 "avoid paying NCCL launch latency on tiny params"。GTP_remat 不切小 tensor，文档写 LayerNorm、bias、MoE router 这些 "always stay full"。

all-gather 出了 NVLink domain 还藏得住吗？

文档写 "One GEMM of runway covers a gather that stays inside the NVLink domain, but not one that leaves it"。MoE 的 routed-expert weight 属于后一种，文档给它们单独的 one-block-ahead chain。

128× 是怎么算出来的？

文档没有给推导。32× 是 TP × GTP_remat = 4 × 8。128 = 32 × 4 对得上 BF16 的 16 bit 换成 NVFP4 的 4 bit，这是猜测。文档 1.3 节的表里 NVFP4 的 all-gather 是每元素 0.5625 byte，对 BF16 的 2 byte 约 3.6 倍，所以面试里只引 32×。

怎么打开，有什么限制，规模到多大？

--tensor-parallel-num-weight-shards 决定 GTP_remat 的大小，等于 1 时 GTP 不生效。文档写它 "composes orthogonally with TP / SP / EP / DDP / CUDA Graphs"，目前要求 num_distributed_optimizer_instances == 1。文档的例子是约 280B 的 hybrid Mamba-MoE proxy 在 GB200 NVL72 上用 GTP64，到 3072 GPU 时 scaling efficiency 仍 "≥93 %"。

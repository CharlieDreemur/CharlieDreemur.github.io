Agent 的改动怎么进生产？
PR、review、canary 各管什么？

英文问法How does a change made by the agent get into production? · Would you let the agent push to production by itself? · What is a shadow-traffic canary, and what happens when it fails?

考过Unity Vector 自己的论文 FlashVector（§4.2 Triggering、§5.1、§5.4）· 推断会问，没有面经原题 · 中文样本里 CI、PR、灰度（canary）和 rollback 这一类只有 10 帖，多为社招，比如快手全栈二面（2026-09）「做灰度时，agent怎么知道什么是异常？」（牛客）和蚂蚁 agent开发二面（2026-09）「agent自动回滚触发条件」（牛客）

先弄清楚：每个概念是什么

Pull request（PR）
把改动打包交出来等人 review，像实习生的代码要先过 code review。
Shadow traffic
把真实请求复制一份发给新版本，结果不返回给用户。
Canary
新版本先小范围试跑，指标稳住了才采纳。FlashVector 的 canary 喂的是 shadow traffic。

看图：从触发到写回

30 秒回答

The agent never pushes to production itself. In FlashVector it opens a pull request for a person to review. Then the change goes through a shadow-traffic canary: real requests are copied to the new version, and its responses never reach users. If the canary holds, the change is adopted; if not, it's discarded. Both outcomes are written back to the knowledge base, so the next run doesn't retry a rejected idea. Runs start automatically when a new release enters the fleet. The paper doesn't say how long the canary runs, what threshold decides it, or who reviews, so I'd ask.

必答点

  • agent 不直接改生产，它开 PR，由人 review
  • shadow traffic 是复制真实请求给新版本，结果不返回给用户
  • canary 稳住就采纳，否则丢弃，两种结果都写回 knowledge base
  • 自动触发：新 release 进 fleet，或模型太久没分析
  • 说得出论文没写的：canary 跑多久、流量比例、阈值、谁 review

追问

为什么不让 agent 直接合并？

论文自己写了 LLM 会把瓶颈归因错，本层通过的改动合到一起也可能回退（见 local 和 end-to-end）。人 review 和 canary 是最后两道检查。

做灰度时，agent 怎么知道什么是异常？（快手原题）

判定不交给 agent。阈值事先写在规则里，由确定性代码判断 canary 稳没稳住。

为什么 config 改动用 shadow traffic 就够了？

config 改动按设计不改变预测结果，只影响 latency 和 throughput，用复制的请求就能量出来。新版本出错也不会伤到用户。
